# RCA B4 : Acceptation d'un code promotionnel expiré

## Symptôme observé

Lorsqu'un utilisateur saisit le code promotionnel `EXPIRED` et clique sur « Continuer vers le paiement », l'application ne présente pas le message d'erreur attendu `Promo code expired`.

À la place, l'utilisateur est redirigé vers la page de paiement et une commande est créée avec une réduction de 15 %.

Le test concerné est `test_expired_promo_code_shows_error`.

## Impact (pour l'utilisateur, pour l'entreprise)

**Pour l'utilisateur :**
- Le système accepte un code promotionnel qui n'est plus valide.
- Le montant de la commande est réduit de manière injustifiée.

**Pour l'entreprise :**
- Perte potentielle de chiffre d'affaires.
- Non-respect des règles commerciales relatives aux promotions.
- Risque de répétition de l'anomalie si le contrôle reste désactivé.

| 2. Pourquoi l'API accepte-t-elle le code expiré ? | Parce que la validation de la date d'expiration ne déclenche pas l'exception HTTP 400. | Réponse API avec `total_cents: 2975`. |

| 5. Pourquoi ce défaut peut-il ne pas bloquer la CI ? | Parce que les étapes Playwright et Selenium utilisent `continue-on-error: true`. | `.github/workflows/ci.yml:51` et `:56`. |

## Cause racine

La cause technique est le contournement volontaire du contrôle RM4 dans la fonction `_validate_promo()` lorsque le mode bugs est activé.

La condition suivante empêche le rejet d'un code expiré :

```python
if promo.expires_at and promo.expires_at < datetime.utcnow() and not settings.seed_bugs:
```

Lorsque `settings.seed_bugs=True`, le contrôle d'expiration est ignoré et le code promotionnel est accepté.

Une faiblesse complémentaire du processus CI est identifiée : les échecs des tests UI Playwright et Selenium sont tolérés par `continue-on-error: true`. Un job peut donc continuer malgré ces échecs.

## Actions correctives

- **Produit :**
  - Rétablir le rejet systématique des codes promotionnels expirés.
  - Conserver une validation côté serveur, indépendamment des contrôles de l'interface.
  - Ajouter un test API de non-régression vérifiant qu'un code expiré retourne HTTP 400.
  - Vérifier qu'aucune commande n'est créée avec un code expiré.

- **Processus de test :**
  - Supprimer la tolérance injustifiée des échecs UI dans le workflow CI.
  - Faire échouer le job lorsque les tests Playwright ou Selenium échouent.
  - Conserver les rapports et les traces Playwright pour faciliter l'analyse des anomalies.
  - Ajouter une vérification systématique des règles de validation des promotions dans les tests API et UI.

## Comment vérifier que c'est corrigé

1. Exécuter le test API avec le code `EXPIRED` et vérifier que l'API retourne HTTP 400.
2. Exécuter le test UI `test_expired_promo_code_shows_error` et vérifier que le message `Promo code expired` apparaît.
3. Vérifier qu'aucune commande n'est créée avec ce code expiré.
4. Vérifier qu'aucune réduction n'est appliquée.
5. Réexécuter les tests UI et API.
6. Vérifier que la CI échoue lorsqu'un test UI échoue.
7. Vérifier que le workflow ne contient plus de `continue-on-error: true` injustifié pour les tests.
